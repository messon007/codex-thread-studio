# Agent Teams 的最小实现方案

> 当前实现与验收见 [implementation status](implementation-status.md)、[host integration](host-integration.md) 和 [实现审查](implementation-review.md)。本文保留早期候选/探针的时间顺序及未通过结论；它们不代表最终适配器状态。

2026-11-18，GPT-6.2-Astra。推荐在**单用户、受信 Codex 宿主**上，用 MCP 实现成员的同步命令，用 Studio 后端的持久队列决定何时向原生队列交接一条已授权消息。两者独立，不要求先给 Codex 增加工具热插拔、队列幂等键或跨应用事务。已有隔离实验支持这条路线的部分前提，尚需 G1b/G2b 检查其余前提。[隔离验证结果](verification-results.md)

**设计裁决为 PASS，分别放行纯领域模块的开发，以及文末 G1b/G2b 两项限定验证。** 领域模块可在 `feat/agent-teams` 用队列替身开发，覆盖状态机、授权角色、任务依赖、问答、验收、事务事件、幂等和 outbox；测试只能证明领域行为。真实接入按两项验证的固定版本与拓扑结果开放。这个裁决不启用产品派发，不批准静默改用户配置或合入 main。本文调整 [原规范](specification.md) 中两处设计前提：成员归属的信任边界，以及授权交接与实际开始的边界。原任务协议、上下文、权限、分组和非抢占要求继续适用。

## 谁可以代表谁

| 主体 | v1 信任及权限 |
| --- | --- |
| 实例所有者及其受信原生客户端 | 所有者已能控制已管理会话和主机，也是 Teams 管理者。正常配置、UI 操作、维护都记为 user。受信客户端负责正确标注原生调用上下文，禁止把成员参数转发为不受约束的宿主直调。v1 提供宿主归属审计，不对所有者本人或其等价权限的程序提供抗抵赖证明。 |
| 现有 Codex 成员 | 一个成员是持久的 backend/thread 引用，业务授权只允许本组规定的操作；在模型输入中自报的来源、角色、cwd、thread/turn 均不作为 caller。其普通文件、命令和审批能力仍由原有会话控制。任意两个同 OS 用户的高权限会话不构成隔离租户。 |
| 其他会话、网页、网络调用者与任务内容 | 无注册身份或无本组绑定即拒绝。工具提示、引用文件和问题文本都不能增加权限。用户管理端、模型工具端使用不同的凭据/传输；成员进程不得被产品主动授予 Studio 用户 bearer 或管理 RPC。 |

第三轮反例来自第二个**已有宿主访问权限**的客户端。它否定了强威胁模型下用事件内容证明“只有这一个真实模型请求”的方案。对一位用户协作管理自己的会话，阻止这位用户刻意伪造自己的宿主事件不是普通成员归属的必要条件。仍须排除另一种情况：可被网页、普通成员命令或自动化随意调用的通用宿主代理，会把低权限主体提升为宿主。只把由实例所有者管理、管理面没有委派给这些主体的入口列入支持配置。用户若主动允许全权限 shell，产品应明确“按受信主机合作记账”，不能宣称能抵御同用户恶意程序；需要不互信租户或独立安全审计的部署使用更强适配，不能通过勾选单用户模式获得这项保证。[Studio 网关](../../src-tauri/src/gateway_security.rs) · [已有反例及其前提](verification-results.md)

## 推荐架构和成员命令

Rust 中分三个责任域。Teams 独立保存 roster、任务、问题、结果、revision/attempt 和逻辑 effect；注册适配层把 MCP 的原生上下文变成可信宿主归属的 actor；通用会话队列管理普通排队输入、来源、顺序、暂停与交接。UI 只发用户命令和订阅状态。最多五个既有 thread，排除 Router 控制会话。一位可选的组内 orchestrator 只改变新组目标的默认接收方，根任务由用户验收；成员间照常直接委派。T1 等待一个 blocking 答案时释放当前执行轮，A 可以领取 T2，也能接收关于 T1 的答复或验收。

| 方案 | 可以交付的体验 | 选择 |
| --- | --- | --- |
| 受信宿主下的同步 MCP | 模型拿到本次 delegate/ask/submit/review 的结构化成功、拒绝或冲突，不等另一成员。现有会话 A 在 0.170.0 测试中重载、发现并执行过 echo。 | **首选**。优先试每成员注册或独立受管配置层。来自该宿主的原生 thread、Turn 和工具事件做归属及防误路由；满足本节威胁模型即可。 |
| 只消费受信原生工具事件 | MCP 标记工具只返回“已收到标记”。Rust 读取真实模型产生的完整结构化 item，验证来源/审批，幂等执行。结果或冲突只定向发送给原 thread。 | 适用于不愿让外部 MCP 请求直接提交命令的部署。需要验证事件来源、持久覆盖与重放；短事务同步响应会变成异步确认，读结果可能多一轮。须专门审订这组接口，避免在未提交时向模型报成功。 |
| 本机动态工具 | 原生 `item/tool/call` 可按宿主请求通道同步回应，适合更强的调用归属。 | 0.170.0 的现有声明入口在 thread/start。只有已具备工具的旧 thread、或未来具有已证实安全重绑定的版本才可用。不能为了工具新建、fork 或复制历史。 |
| Hooks/CLI | 可选提示，或展示用户可见的状态。 | v1 无需安装。运行命令的普通进程没有独立成员身份；也不能用 prompt hook 或读取聊天文本作为消费权。 |

**装载和调用**

1. 启用组时，按组内真实 backend/thread 做绑定，记录原生 thread、现有会话模型、cwd、权限/审批及上下文标记。忙碌会话等安全边界。首先实验在同一 thread 的 `thread/resume.config` 中仅增加自有 MCP 注册；schema 接受 config overrides，是否对已加载 thread 生效、是否跨客户端恢复仍待查。不要在 resume 中传模型、cwd、审批或 sandbox 覆盖。配置失效、换代或会话只读历史不可继续时标记该成员未就绪。
2. 若按 thread 装载不可用，可使用用户**已有或明确为 Studio 配置**且与普通用户配置隔离的受管层，检查注册所有权、影响范围和可撤回性。恢复的仍须是原有 thread 并与其现有运行权一致，不能让另一个进程同时执行同一存档。用户全局 MCP 注册会改变其他会话的工具目录，不能作为自动回退。两个装载途径均不满足时保持 held。MCP 类型可用受信 stdio 适配或受认证的本地服务；不要把工具参数、成员 token 放进提示或源码。参考 [App Server 的原生模型与工具接口](https://learn.chatgpt.com/docs/app-server)。
3. 优先将专属注册/连接绑定到 `{instance,backend,thread}`。若适配是实例共享的，则其认证只说明来自该 backend；成员身份另由受信宿主填入的 thread 和对应的活跃模型工具事件产生。用当前注册代数、thread、turn、call/item、tool、规范化参数匹配，按相同键去重。不得从模型业务参数推断 caller。缺少或矛盾时有界等待后拒绝。只读也做同样检查；宿主诊断调用只走无业务数据诊断接口。结果显示“由 Codex 宿主归属到会话 A”，用户在 UI 代为验收单独标 user。
4. 例如在 A 的现有 Turn 调用 `team_delegate(group_id,request_id,to_member_id,title,request,acceptance,…)`。受信上下文给出 A，服务事务校验权限，保存任务 T、初始 attempt、事件和 effect，立即将 `{task_id,revision,effect_id}` 返回 A。B 的实际通知由队列独立发送。B 收到后 get/begin；阻塞时 ask/checkpoint 后结束该任务本轮，答复与其他工作都能排队。submit 只入待验，原规范的提交 Turn 屏障、review 与父依赖释放继续适用。模型拒绝、工具未调用、native Turn 完成都不能代替提交/验收。
5. 关闭时先撤销新成员命令，保留精确到成员/任务/批次/Turn/claim 的已开始回执资格；回执只落事实，后继 effect 挂起。职责更新只产生小型队列通知。待限权回执完成或人工处置后撤自有注册；普通会话与 UI 的启动不依赖 Teams。

## 单次授权交接给原生队列

**真正需要新增的是 Studio 后端的持久排队与保留裁决。** 现有页面维护队列数组、暂停集合、运行集合和监督 Map，Rust 目前按会话替换整个 JSON。复用其会话身份、持久化框架、原生生命周期及普通队列 UI，并在通用入口引入稳定消息 ID、顺序与版本。多个页面不能分别消费或覆盖彼此刚写的队列。Teams 本身只调用端口，既不实现第二个调度器，也不直接发起 turn/start。普通用户主动发送/Steer、普通队列的附件和选项、Router 的既有行为应有兼容检查。尤其是 native queue/add 不能携带普通用户的所有逐轮覆盖选项，迁移通用排序不要求粗暴地把各种用户输入都改写成同一原生调用。[队列消费](../../ui-src/submission-controller.mts) · [持久化](../../src-tauri/src/session_state.rs) · [页面级监督](../../ui-src/turn-supervision.mts)

| 通用接口 | 持久契约 |
| --- | --- |
| `admit(session_ref, source, stable_id, message, scope_generation)` | 按 `(session_ref,source,stable_id)` 幂等创建本地条目、分配 enqueue_seq。Teams 的 stable_id 是已物化的 delivery_id。普通用户输入保留其原始相对顺序。 |
| `reserve(session_ref,owner,generation,reason)` / `release(reservation_id,generation)` | 监督逻辑任务、人工暂停、失败/审批停顿有持久记录。owner 明确释放或经核对后释放；页面掉线、子 Turn completed、超时均不会自动释放监督保留。 |
| `authorize_head(session_ref)` | 在队首且 scope/attempt 有效、无阻断、没有上一项交接待核对时，事务内登记一次性 dispatch_id 和稳定 clientUserMessageId。把授权与 scope fence、保留请求排序。每个会话同时最多一个已经交接但尚未确认已开始的 Teams 项，限制关停时的未决集合。 |
| `submit_authorized(dispatch_id)` | 先持久写“准备调用、可能已发送”，唯一消费者只向该 thread 的 `thread/queue/add` 提交一次。成功记录服务端 queuedSubmission.id，保持“原生已排队”；等待原生自动消费。无须调用 queue/start、turn/start、turn/steer 或 interrupt。 |
| `fence_scope(scope,generation,intent_id)` / `lookup(stable_id)` | 撤销未来领取，返回本地可撤、已原生排队、已开始、未知的分项回执。重复 fence 读取原有记录。取消与暂停通过此端口取得同一顺序上的裁决。 |

**四个边界不能混写。**

1. **忙碌与顺序。** T 可以立刻进入 Studio 持久队列。默认等权威观察表明目标无活跃工作后才领取，缩短原生交接窗口；若用户在此检查后先启动一轮，使用的仍是 queue/add，它必须只追加独立后续轮次。关键验证落在 add 的所有支持路径，不能把已观察到的 queue/start 拒忙移用给 turn/start 或 add。0.170.0 的 TurnStartParams.turnTrigger 字段说明还提到 turn/start 在某些情形会 Steer 活跃轮次，彻底避开这条路径。外部 CLI 自己已在原生队列的人工项遵守原生顺序；本地待办尚未交接时不宣称已取得外部队列位置。若需要所有客户端按现实提交时间的严格全局 FIFO，则必须让它们经过同一入口；本方案保持 Studio 队列次序和既有人工项的相对顺序。
2. **监督。** 已开启的监督必须在根任务可能进入轮间空档之前登记 reserve，与 authorize_head 同序。只要监督仍持有保留，绝不将 Teams 正文放入会自动推进的 native 队列。若通知已交接，用户随后才为某项工作开启监督，则优先按原生条目 ID 撤回尚未开始的通知；不能证明撤回时，显示“正在建立监督，先核对此在途项”，不能报告监督已经独占。原生已经开始时不强停。这是后来请求保留与在途工作的显式竞争结果。能从外部 CLI 正常使用 thread，不代表 Studio 能看见任意外部工具自定义的跨轮“逻辑任务”。需要同样保留语义的外部监督者须登记其 reservation，不能承诺替未集成的监督器猜测何时完成；已知存在无法观察的保留时分成员停止自动投递。
3. **暂停/取消/关闭。** 收到停止请求先持久 fence，本地未交接条目立即 held/withdrawn；已授权但可证实尚未发起 RPC 的条目仍可撤。已知原生排队的项按其服务端 ID 精确删除并核对，不得触碰普通消息。取消任务立即禁止其新的 begin/submit；暂停/关闭仍保留原规范允许的已开始工作限权回执；在途原生输入可能同时获消费，接收者必须 get/begin 后才执行任务。UI 区分“已停止派发”“正在撤回原生待办”“已开始”“无法确认”。只有未开始项均明确撤回、其余已确认真实开始/结束，才报告严格意义的关停完成。未知项保守冻结，关闭的新授权立即生效；没有后台自发继续工作。只要业务要求从点击取消那刻起、连先前原生已接纳的消息也绝不产生新的 Turn，应用层无法作这个更强承诺，需要原生消费点支持。本文不把“已授权但仍在排队”改名为“已经开始”。
4. **崩溃与重试。** 应用 outbox 到本地队列可以用相同 delivery_id 安全补投，原生 add 不得按同一规则重发。写发送意图前崩溃可从本地重启；写意图后断线、超时或在收到成功前崩溃，一律 unknown。在原生队列、历史及事件中用稳定 ID 查证；队列唯一命中且内容/recipient 正确可补记 receipt，匹配的原生 turn 证实开始。查无、匹配多个、仅正文相同、或底层不保留该 ID，都不足以证明没执行，继续冻结自动重发。只有权威证据证明请求未提交/被原子拒绝，才重新排入本地队列。人工可记录凭证或放弃不确定项。每个 UI 事实写明对应的 receipt；底层未保证 exactly-once 时，产品用“可能漏送、显式核对”换取不重复执行。

Studio 对域内自动派发有一个决定何时交接的点，Codex 对原生何时开始有另一个决定点。首次授权前一直只在 Studio 保存正文；已授权输入由原生负责顺序并允许自然消费。**相对原规范，撤销经受保护队列一直有效到交接，交接后为精确删除、竞争核对及领域 claim 门控。** 原规范要求的“任何原生消费前再同步检查 Studio epoch”在此方案中没有实现。这项差异对用户表现为短暂的停止收尾以及可见的不确定项，不能在产品说明中省略。若部署要求保留严格的原生消费回调，继续使用旧标准并关闭该适配。

## 验证、实施与需要上游的情形

| 项 | 最小实验与放行标准 | 失败后的实际行为 |
| --- | --- | --- |
| G1b 旧 thread 与工具归属 | 使用相互隔离的测试配置及两个**事先存在**的 thread，先测每 thread 配置；另有普通非成员作旁观对照。证明重载前后的 ID、原上下文、cwd、模型、权限/审批保持，非目标配置未被修改。对每位成员在同一 backend 的不同 Turn 调用只读工具，检查归属、错组拒绝、缺事件/换代拒绝、并发调用结果归还原连接；成员端/网页无用户控制能力。禁用后新命令拒绝，普通会话继续。实证环境限定为上述受信宿主模型。至少一次真实模型在测试旧 thread 自主调用并读到合成业务结果，才能对外说模型接入已通过；确定性的合成流可先证明协议。 | 只有明确的受管独立配置层可作为装载备选；无法保持原 thread 和权限则该成员未就绪。无需用强宿主冒充场景反复否定单用户模式。 |
| G2b 持久一次交接 | 以无副作用标记覆盖目标闲置、长时间忙碌、审批/用户输入等待中，以及两个客户端同时提交人工输入与 queue/add。除原生队列开始外对 Teams 路径不调用任何 Turn 控制。验证原工作无注入、无打断、无额外并发 Turn；原生人工队列前后次序清楚。分别让 reserve/fence/授权先赢，覆盖两个监督 Turn 之间、排队后撤回、开始后撤回、RPC 前后掉线和重启。核对只提交一次、已知/未知有据、无法核对就停止。无真实宿主保证的竞态注明其范围，结合目标固定版本的消费实现/受支持契约核实“add 不注入当前 Turn”。 | 忙时有注入的路径禁止自动投递。某些恢复场景无法取回 ID，可保持 unknown 交给用户；这本身不等于系统必须重发或改上游。 |
| 原会话与可选模块回归 | 域测试和受控队列证明 A 等 T1 仍做 T2，协调者普通成员直派、最多五人、关停在途、重启、普通手动消息、原 Router 均符合规范。实际运行再确认一次委派→问答→结果→验收，无用户工作区写入副作用。 | 域测试可先独立推进；真实派发按通过证据的 backend/版本开启，默认关闭。 |

**开发边界。** 可以立刻实现与适配器无关的 Rust 领域事务及测试；新 G1b/G2b 的探针依旧放 `/media/rui/codex-thread-studio-agent-teams/` 专用配置、数据和缓存。共享队列改造单独交付，可先以替身验证单写入方、稳定顺序、reservation 和控制面阶段回执；改变普通队列消费前完成旧持久数据和多页面兼容回归。G1b/G2b 通过后，在对应拓扑接入原生 adapter 并验证端到端，再开发/开放独立 UI；满足上述前提的单用户部署可按验证结果启用对应能力。在前提未满足的部署，UI 可继续显示任务、待投递、人工核对及未就绪原因，不后台发送半可用命令。

**上游只在额外能力确属不可替代时需要。** 例如部署必须在存在不受信的已认证宿主客户端时仍给出逐调用不可伪造身份；普通已运行旧 thread 没有安全的工具装载方式且也不能使用受管层；所有客户端必须共享消费前可撤销的本地 epoch 和监督权；或至关重要的原生 queue/add 路径会向忙碌 Turn 注入且无其他独立排队原语。此时应精确请求逐调用响应绑定、已有 thread 工具装载或原子排队/撤销能力。普通单用户协作采用上述候选即可开始分层验证和域开发。任何回退都不新建第六个 Agent，不修改全局 Router，不用 Steer 唤醒成员。
