# Native Thread Router specification

## Purpose and boundary

Thread Router is a fixed inbox that classifies one user request and dispatches it to exactly one existing session. Routing depends on the session catalog and each session's responsibility, not on its backend. The controller can currently run on Codex or OpenCode, while targets may independently belong to either backend.

Studio does not read Agent Deck configuration, invoke Agent Deck commands, attach to tmux, or require a bridge daemon. It does not split one request across targets or queue work behind a busy target.

## Configuration and identities

Each ordinary session owns its optional routing responsibility in **More → Session information**, beside the editable opening question. The responsibility can be edited directly or generated by AI from that session's conversation; generated text is placed in the field for review and is not saved until the user confirms. **More → Router settings** is limited to at most three fallback targets. Each fallback has an editable condition, defaulting to “No regular session is suitable for the user query.” Every target not listed there is a regular target. The decision backend is intentionally not switchable in the UI.

To change it, close Studio, edit `router.controllerBackend` in the Studio settings file (`~/.config/codex-thread-studio/settings.json` on Linux) to a registered backend such as `codex` or `opencode`, then restart Studio. Studio creates or recovers that backend's controller during startup. The `controllers` map is managed by Studio and should not be edited manually.

Session identities are stored as `backend:id` (for example `codex:abc` or `opencode:abc`). This prevents collisions and keeps routing policy independent from backend protocols. Controller identities are stored per backend so a configuration-file switch can reuse its native history. Only the configured controller is shown in the sidebar; inactive controller histories remain stored but hidden, so the **ROUTER** group always contains exactly one Router session. Old Codex-only settings are migrated in memory: descriptions move to per-session responsibility metadata and old fallback roles become fallback entries.

The controller lives in Studio's dedicated Router workspace and is excluded from the target catalog. Its backend-native session contains only user requests and structured routing decisions. The Rust gateway validates settings; no credentials or copied response history are stored.

## Dispatch contract

The catalog supplied to the controller is intentionally similar to a concise Skill header. Each entry contains only the stable session key, backend, title, directory, captured opening message, responsibility, and—only when configured—the fallback condition. This bounded description is sufficient for selection without loading target transcripts.

The controller does not solve the task or call tools. Studio injects the complete bounded catalog through the Codex Turn's application `additionalContext` (or the target backend's equivalent system context), rather than relying on a sticky Thread-level developer prompt. It returns a schema-constrained object containing `action`, `targetSessionKey`, `forwardedPrompt`, `reason`, and `message`. For every Turn, `action` is fixed to `dispatch` and `targetSessionKey` is constrained to an enum containing only the exact backend-qualified keys in that Turn's catalog. Explicit target references win, followed by the most specific regular responsibility match. Only when no regular target is suitable may the controller consider a fallback whose condition applies; otherwise it chooses the closest regular target instead of asking the user to clarify.

```text
User → active Router controller
  → refresh bounded session catalog
  → native structured controller Turn
  → dispatch
          → validate backend:id against the supplied catalog
          → prepare and read target through its registered backend adapter
          → reject a busy or missing target
          → send forwardedPrompt as a normal target user message
          → immediately release Router for the next request
          → observe only the target Turn's terminal state
```

The dispatch registry requires adapters to implement `read` and `startTurn`, and offers an optional `prepareTurn` lifecycle hook. Codex uses the hook to resume a persisted thread before `turn/start`; backends that can start directly leave it empty. Router policy contains no Codex/OpenCode branch; adding a backend means registering an adapter and exposing its sessions in the catalog.

## Presentation and completion

Router is a specialized protocol session rather than an ordinary transcript. While its controller runs, reasoning, partial text, and incomplete JSON remain hidden behind a routing-status card. A valid result renders only the selected session, concise reason, and dispatch state. Dispatch does not block the next Router request. Studio tracks the target Turn only until its terminal state, then changes the card to **Target completed** (or failed) and exposes **Open response**. The response body is not copied into Router history. If and only if the controller decision is invalid, the failure card offers a bounded, escaped **View raw decision** diagnostic so the bad payload can be analyzed.

The forwarded request is a normal user message in the target's native history. Opening the link switches to the correct backend and session and scrolls toward that Turn; the target window therefore contains the full request, response, tools, file changes, approvals, and stop reason.

Runtime completion links are best-effort UI state and are not separately persisted. After restart, routing decisions remain reconstructable from controller history and appear as routed cards.

## Failure behavior

- No targets: do not start a controller Turn; report that no routable session exists.
- Invalid or out-of-catalog key: show failure and do not dispatch.
- Busy or removed target: show failure; never steer or interrupt it.
- Backend unavailable: show which routing or target backend failed.
- Disconnect during execution: reconcile through native history; never automatically replay a prompt.

## Acceptance criteria

1. A controller is created only when its configured backend has no stored controller identity; configured identities are reused and never silently replaced.
2. Responsibilities are edited per session, use backend-qualified keys, and targets from Codex and OpenCode can coexist, including identical native IDs.
3. Either Codex or OpenCode can make the structured decision without constraining the target backend; changing it requires a settings-file edit and restart.
4. A valid decision starts exactly one normal Turn in the target without changing the selected session.
5. The target receives the forwarded prompt as a visible user message and retains the complete native response.
6. Router becomes writable after dispatch and does not wait for target completion.
7. Completion updates only the Router card and link; it does not copy target response content.
8. Invalid keys, missing targets, busy targets, and unsupported backends never start unintended work; an imperfect semantic match still chooses one catalog target rather than asking for clarification.
9. The implementation has no Agent Deck, tmux, or conductor dependency.
10. The sidebar shows only the configured controller even when native controller histories exist for multiple backends.
11. Router settings accept no more than three unique fallback sessions; all unlisted sessions remain regular targets.
